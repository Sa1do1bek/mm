# Централизованные сопоставления MM → 1С

Для организации, работающей с новым CF, укажите на сервере MM путь к JSON-файлу в свойстве Spring `mm.one-c-api.native-posting-profile-path`. Например, в окружении контейнера задайте `MM_ONE_C_API_NATIVE_POSTING_PROFILE_PATH=/run/config/mm-native-posting.json` и примонтируйте файл с этой стороны контейнера. Свойство читает профиль при запуске MM. Он не содержит реквизиты авторизации. Tenant и компания должны совпадать с авторизованной областью подключения 1С.

```json
{
  "tenantId": "<tenant MM>",
  "companyId": "<UUID компании MM>",
  "nativePosting": {
    "organizationRef": "<UUID организации 1С>",
    "transitWarehouseRef": "<UUID транзитного склада 1С>",
    "receipt": {
      "supplierRef": "<UUID поставщика 1С>",
      "contractRef": "<UUID договора 1С>",
      "contraAccountRef": "<UUID счета расчетов 1С>",
      "subconto1Ref": "<UUID поставщика для аналитики 1С>",
      "subconto2Ref": "<UUID договора для аналитики 1С>"
    },
    "issue": {
      "expenseAccountRef": "<UUID счета затрат 1С>",
      "expenseCodeRef": "<UUID шифра затрат 1С>"
    }
  },
  "warehouses": {
    "<UUID склада MM>": "<UUID склада 1С>"
  },
  "materials": {
    "<UUID материала MM>": {
      "nativeMaterialId": "<UUID номенклатуры 1С>",
      "nativeAccountId": "<UUID складского счета 1С>",
      "nativeUnitId": "<UUID базовой единицы 1С>"
    }
  }
}
```

Профиль задаёт UUID 1С для одного tenant и компании на экземпляр бэкенда. Для перемещения должны быть сопоставлены склады отправления и назначения. Каждая строка должна иметь сопоставление склада и материала, складской счёт и базовую единицу 1С. Разделы `receipt`, `issue` и транзитный склад проверяются по виду документа.

MM дополняет ранее не выдававшийся документ при первом опросе. Если сопоставление отсутствует, сохраняется причина `MAPPING_REQUIRED` и задача не выдаётся. После обновления профиля и перезапуска бэкенда очередь повторит попытку. Сопоставленные UUID сохраняются в исходящем событии и повторно используются для подтверждения и повторных попыток. Уже выданные задачи v1 обрабатываются прежним клиентом с локальными таблицами до перехода. Клиент с `nativePostingV1=true` получает только разрешённые задачи документов; для чтения склада и сверки используются снимки v2. Настройка Basic Auth остаётся отдельной.

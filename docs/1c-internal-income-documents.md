# Internal income documents

Warehouse execution has two material receipt sources:

- Supplier receipt: an active supplier contract and its specifications.
- Internal receipt: an existing transfer document addressed to the receiving warehouse. Creating, approving and dispatching new documents stays in the transfer workflow; receipt uses the existing shipment allocations, version checks and idempotent posting.

`_document9907` (Служебная записка) contains no rows in this snapshot. Its metadata relates to payment documents; it is not treated as a verified warehouse receipt basis. The similarly named internal railway invoices are not warehouse transfers.

A follow-up read of `_accumrg9940` (Учет служебных записок) found 11,546 active register entries despite the empty document table. Of these, 7,001 belong to the single register-adjustment document `СБ000000009`, dated 2020-12-31 23:59:59. Its comment is `УчетСлужебныхЗаписок:[Сформирован обработкой свертки базы][Ввод остатков по регистрам накопления]`: these are opening register balances generated by database roll-up. The other 4,545 entries belong to payment orders and all have an empty basis reference. None of the register basis references resolves to an existing `_document9907` document. This proves retained accounting history and a roll-up, not that service memos were never used; the snapshot alone cannot establish how each original memo was removed or where its full text is retained.

For transfers, `_fld1993rref` is the sending warehouse. If header `_fld5251` is true, the receiving warehouse comes from each line's `_fld5252rref`; otherwise it comes from header `_fld2000rref`. The snapshot contains stale line destinations when the switch is false, so using an unconditional line/header coalesce is incorrect. A destination in the table that has no managed warehouse mapping is excluded, without falling back to another warehouse.

For internal receipts, `_fld2492rref` is the receiving warehouse. This type has no direct sending warehouse field; no sender is inferred from accounting subaccounts. Source quantities remain exact decimal strings. Units resolve from the original line unit reference (`_fld2007rref` / `_fld2515rref`) through the imported `1C-UOM-<source-id>` master, not from the material's current stock unit.

## Application integration

`GET /api/workspaces/warehouse-execution/income-documents/1c?warehouseId=...&search=...&page=0&size=20` lists document numbers, dates, original types, requirements and original posted/deletion states. Search matches document or requirement numbers literally. `GET /{id}?warehouseId=...` returns only the receiving warehouse's lines, with materials and original quantities.

Both reads enforce the current tenant, company and warehouse assignment. Only records from completed history imports are used. Multi-destination documents expose only requirements and lines addressed to the selected warehouse.

All snapshot records are historical evidence, including unposted, future-dated and deleted documents. They cannot initiate receipt or be converted automatically into a live transfer. Historical movements/opening balances have already been imported separately, so replaying them would duplicate stock. This integration adds no posting endpoint and performs no new stock import. New live receipts use new system transfer documents.

The warehouse income dialog exposes the current receiving queue and the 1C documents as separate tabs. It requires selecting a document before receipt; sending/receiving warehouses and materials are read from that document. No supplier contract or arbitrary source warehouse selector is used for internal income.

The warehouse execution panel also exposes an Internal transfer action. Authorized preparers can create a new document with the panel's warehouse fixed as its source, then submit it and continue the existing lifecycle in the embedded transfer workspace. The income dialog's Transfer documents button opens this workspace in the same panel. Creation preserves the receiving/sending panel's warehouse and company context; the existing role and approval rules continue to apply.

Validation covers PostgreSQL query execution, header/table destination rules, tenant/company/warehouse isolation, incomplete imports, literal search/pagination, exact quantities and historical immutability. Browser checks cover supplier contracts, document selection, 1C requirement lookup and partial receipt of a real shipment allocation.

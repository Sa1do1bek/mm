# Kimyosanoat warehouse issues in MM

For the inbound exit event contract and sender handoff, see [kimyosanoat-event-handoff.md](kimyosanoat-event-handoff.md).

## Workflow

The Kimyosanoat backend exposes a read-only, organization-scoped transfer feed for MM. A transfer enters the feed after an `EXIT_ACCEPTED` event. MM checks the current source lifecycle and final quantity again before an issue is posted. The warehouse workspace displays the buyer, source warehouse, material, final exit weight and available transport and loading details. A manager can choose an owned stock position; approval creates and posts an MM issue for that exact batch.

The inbound receiver accepts the original Faktura `local_waybills` JSON bytes on `POST /api/integrations/kimyosanoat/events` with MM Basic authentication. It stores a receipt even without source identifiers; such a receipt requires review and cannot post stock. With `X-Transfer-Id` and `X-Warehouse-1C-Id` headers and exactly one waybill, it creates an `EXIT_ACCEPTED` work item. The older five-field event JSON remains accepted for compatibility. The sender's current guide describes a Faktura request attempt, which does not itself establish that the source transfer is final; Kimyosanoat must bind the headers to a final transfer before automatic stock posting can occur.

When `app.kimyosanoat.webhook.auto-post-enabled` is enabled, a background worker re-reads source detail and posts through the same source claim and stock movement path only when one imported warehouse, one N-code material, and one owned batch position with enough stock are unambiguous. Source outages retry with backoff. Unclear or ineligible cases enter `REVIEW_REQUIRED` with a reason; the warehouse workspace displays the reason, and MM administrators can inspect and retry events via the review API. The production configuration has this flag enabled, subject to deployment.

MM enforces its warehouse access rules on both list and approval requests. The source transfer is claimed in the same database transaction as posting; retries return the existing issue, and concurrent approvals cannot create a second issue. The source evidence is retained with the issue. Changed source evidence, changed product mappings, or an issue that is no longer posted are shown for reconciliation rather than posted again. Deleted source records disappear from the feed and require separate reconciliation. A source change between the final source read and MM commit cannot be prevented across the two independent systems.

## Configuration

1. Deploy the Kimyosanoat backend changes before enabling the integration in MM. The source API is `GET /api/v1/mm-issue-transfers` and `GET /api/v1/mm-issue-transfers/{id}`, both requiring a source `warehouseId`. The feed exposes active transfers with historical exit confirmation and their current lifecycle.
2. Create a dedicated Kimyosanoat user in the relevant organization with `ROLE_NAVOIYAZOT_MM_INTEGRATION`. This is an ordinary non-human login that MM uses to read the feed; it is separate from warehouse managers' individual MM logins. The role is restricted to authentication and the read-only integration feed. The existing warehouse-manager role can also read its assigned warehouse, while the dedicated role can cover multiple warehouses in its organization without broader admin permissions. The source administrator must provision the account; credentials are not included in the code.
3. In MM integration settings for the intended tenant and company, enable Kimyosanoat, disable mock mode, set base URL `https://api-navoiy-azot.uzkimyo.uz/be/api/v1`, and enter the source account's username and password through the existing protected settings UI. MM sends HTTP Basic credentials on each feed request over HTTPS; no bearer-token login is used. The MM client accepts only this HTTPS host. The source limits the feed to 600 requests per IP per five minutes, shared between list and detail requests; deployment-wide enforcement requires the existing distributed rate-limit setting and Redis.
4. Imported warehouses are resolved by their retained 1C source identity using the Kimyosanoat warehouse lookup. MM converts its raw 1C database reference to a UUID string; verify this matches Kimyosanoat `warehouse1CId` in the target environment. The feed supplies the product's `productNCode` as text. MM matches it exactly, retaining leading zeroes, against the imported 1C finished-product catalog (`_reference55`) and requires one unmarked, non-group profile with a consistent MM material link. Missing, duplicate, unbound, or deleted identities block approval. No additional 1C sender field is required.
5. Apply the MM database migrations through `V101__kimyosanoat_waybill_inbox.sql` through the normal deployment process. Ensure warehouse managers are assigned the appropriate MM warehouse. The sender must add the two source identity headers to its MM POST and provide reliable delivery; its current in-memory queue has no automatic retry.

`V101` replaces the waybill inbox's earlier `V99` filename because `main` already uses `V99` for the procurement plan backfill. Before release, inspect the target database's `flyway_schema_history`: if the waybill inbox was already applied under `V99`, reconcile that history and the existing table before applying this renumbered migration. Do not run the table creation twice.

## Supported documents and reconciliation

Posting supports ordinary mass transfers with explicit exit confirmation and a positive final net weight, when the matched MM material uses kilograms or metric tonnes. Kilograms are converted exactly to the material's stock unit; quantities exceeding its configured stock precision are rejected rather than rounded. Documents with missing/ambiguous matches, unknown units, non-mass quantities, internal transfers, cylinder handovers, re-entry, administrative closure or deleted state are not posted. There is no automatic correction or reversal of an already posted MM issue; changed source documents must be reconciled through an explicit, auditable process.

The feed is paginated by transfer creation time and is a live view, not a durable event stream. Refresh to see current state, including after source corrections. Managers must have enough available owned stock in one selected position; the system does not combine balances automatically.

## Verification

Automated tests cover source role and warehouse access, eligibility and source changes, MM access and mappings, insufficient stock, PostgreSQL claim concurrency and rollback, and real MM issue posting and retry. The front-end queue and approval flow were also exercised with local synthetic data. See the relevant test classes in the two repositories for the exact cases.

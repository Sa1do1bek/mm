## 2. Варианты

1. **Рекомендуется: развить существующие документы и добавить единый сервис обеспечения.** Сохранить планы/циклы/approval engine/PR allocations/резервы. Выделить расчёт по датам, решения покрытия и количественные связи в небольшие сервисы; старые MRP/availability экраны используют их результат. Плюсы: совместимость и одна истина для склада/закупок/отчётов. Цена: согласование контрактов с 01,03–08,10,11 и явная миграция старой семантики.
2. **Локально расширить существующий MRP и формы.** Быстрее добавить даты и кнопки продления, но останутся несколько несовместимых формул, потеря источников при консолидации и неуправляемые overlaps. Пригодно только как временное чтение текущего состояния; не удовлетворяет всему MM-02.
3. **Отдельный внешний planning engine.** Полезен для масштабного оптимизационного планирования, но потребует синхронизации, отдельного авторитетного состояния и новых эксплуатационных средств. Для данной задачи избыточен; производственный MES передаёт потребности, MM отвечает за их материальное обеспечение.

## 3. Предлагаемая предметная модель

### 3.1 Потребности, версии и консолидация — MM-02-01

Существующая DemandPlanItem остаётся стабильной бизнес-идентичностью. Добавить DemandItemRevision: номер версии, requested/approved quantities, даты, причина, автор/согласующий и связь с предыдущей версией; approved snapshot неизменяем. Новое согласование использует общий approval engine и separation of duties. Правка DRAFT свободна в правах автора; изменение APPROVED/ACTIVE создаёт revision DRAFT и не меняет действующее обеспечение до утверждения.

Решение по строке имеет явное состояние UNDECIDED/APPROVED/PARTIALLY_APPROVED/REJECTED: запрос10, согласование0 с причиной означает REJECTED и не попадает в обеспечение после утверждения родительского плана. Запрос10, согласование6 сохраняет requested10/approved6; разница4 видна как неутверждённая, а не как складской дефицит.

DemandScheduleLine хранит дату, requested/approved quantity, warehouse destination, UOM snapshot и ссылку на revision. Явная operational needByDate даёт один operational slice; месячный план без детализации — по одному slice на ненулевой месяц с precision=MONTH. Месячную дату для консервативного расчёта брать первым разрешённым днём месяца и явно показывать «месяц, срок требует уточнения»; выполнять резерв/перенос/закупку только после подтверждения срока. Сумма slices равна количеству revision, одна и та же строка не учитывается одновременно как месячная и точная потребность. Дроби распределять по точности ЕИ с остатком в последнем выбранном периоде; сериализованные штуки остаются целыми.

Добавить ConsolidationRun + ConsolidationSourceAllocation и команду preview/commit. Группировать по tenant/company, материалу и base UOM, складу назначения, сроку (точная дата либо месяц), разрешённому special-stock purpose, request/line type, budget/currency ограничениям закупки. Разные проекты/заказы не теряют earmark: физическое объединение закупки допустимо лишь с раздельными исходными allocations. Межфирменного объединения нет. Итоги вычисляются сервером из согласованных revisions; повтор commit возвращает тот же run. Повторный расчёт после правки создаёт successor run, а не переписывает источники.

Уменьшение согласованного количества ниже net issued запрещено. Уменьшение выше net issued, но ниже уже обеспеченного, сначала выдаёт impact preview: какие резервы освободить, какие закупочные/transfer обязательства изменить. Stock reservations могут освобождаться атомарно с утверждением; для отправленного PO/отгруженного transfer требуется согласованная компенсирующая операция владельца документа. До неё revision имеет APPLY_PENDING и прежняя approved revision остаётся действующей. Не отменять PO молча из потребности.

### 3.2 Расчёт по датам — MM-02-02

DemandCoverageCalculationService — один детерминированный алгоритм. Вход: tenant/company/разрешённые склады, asOf, горизонт (по умолчанию 90 дней, максимум 366), версии политик и источников. Расчёт получает согласованный snapshot БД; результат содержит generatedAt, source versions, data-quality flags, дневные buckets, строки спроса/поступлений, причины включения/исключения и ссылки на документы. Просмотр ничего не резервирует.

Правила netting:

1. Канонический спрос — approved schedule quantity − net issued − явно отменённая ещё не исполненная часть. PR и PO, возникшие из того же спроса, не создают дополнительный спрос. Самостоятельная PR без demand-origin видна отдельно как LEGACY_UNLINKED; не добавлять её автоматически к потребности того же материала. Требуется явное сопоставление либо отдельный источник.
2. Стартовый свободный пул — eligible AVAILABLE quantity по полному stock key. Он уже исключает резервы/карантин/блокировки. Резервы для данной потребности дают ей отдельное закреплённое покрытие; вычитать из её непокрытого спроса ровно один раз. Резервы других заказов недоступны.
3. Поступающий пул — неполученные/неотменённые остатки подтверждённых PO schedule lines и подтверждённых межскладских поставок, с expected usable date, складом, владельцем, ЕИ. Карантинный receipt становится доступным только по факту разрешения 08. ASN и PO schedule одного потока не суммировать; ASN уточняет дату/состав. Неподтверждённые PO, PR и drafts — отдельное tentative/intention покрытие, не on-time availability.
4. Сначала сохранить действующие explicit allocations, затем распределять незакреплённые доступные пулы по dueDate, priority (внутри одной даты), approvedAt, стабильному ID. Материал с истечением срока до needByDate непригоден. Нельзя дважды предложить один свободный остаток двум строкам в одном расчёте; рекомендации разных расчётов не являются блокировкой и перепроверяются при commit.
5. Для каждой строки/даты выводить onTimeCovered, shortageAtDue, lateCovered и stillUncovered. Поставка после срока не уменьшает shortageAtDue. При распределении поздней поставки на backlog фиксируется одна связь: её количество уже недоступно последующим потребностям. Исчезновение дефицита после даты поставки не стирает историческую просрочку.
6. Страховой запас — отдельная политика пополнения, не второй спрос поверх той же нормы. Показывать hard shortage по утверждённым потребностям отдельно от policy gap. Draft PR/intention уменьшает только число предлагаемых новых PR для того же gap, но не hard shortage и не firm coverage. Повтор nightly run не создаёт новую заявку на уже зарегистрированное намерение.

Отсутствующая дата, ЕИ/коэффициент или destination warehouse даёт UNPLANNABLE с причиной, а не ноль или выдуманный срок. Просроченный PO без новой подтверждённой даты — late/unknown, не поступление «сегодня». Поступление считается пригодным в начале operational date только если его usable date явно так определена; доставка с входным контролем получает отдельную дату доступности. Календарь/часовой пояс — компании, default Asia/Tashkent, события хранят UTC instant.

### 3.3 Нормы и точки заказа — MM-02-03

StockPolicy хранит material/company, scope COMPANY_DEFAULT либо warehouse, effectiveFrom/To, base UOM, min/max/safety/critical/emergency/reorderPoint, leadTimeDays, safetyReleaseMode, approvedBy/version. Точный склад перекрывает company default, fallback в существующие поля Material допускается только как помеченный LEGACY_DEFAULT. Не размножать старую company норму на каждый склад автоматически. Для компании без распределения нормы по складам политика считается по компании и создаёт одно предложение с необходимостью выбора destination.

Предложение по умолчанию для согласования: `0 ≤ emergency ≤ critical ≤ safety ≤ min ≤ reorderPoint ≤ max`; leadTimeDays ≥ 0, ноль допустим для немедленного местного пополнения. Неизвестный срок — null, а не ноль. Критический уровень означает ускорение снабжения, аварийный — эскалацию руководителю. Эти уровни являются порогами одного запаса, не отдельными суммируемыми buckets. Расход ниже safety обычной потребностью по умолчанию требует override с причиной; emergency priority не позволяет забирать чужой резерв.

На дату `asOf + leadTimeDays` считать projected eligible balance после firm demand/supply. При достижении reorderPoint предлагать пополнение до max: `max(0, max − projectedBalanceAtLeadTime)`. Ранний hard shortage показывать отдельно с требуемой датой и опозданием lead time, не скрывая его дальним пополнением. Кратность заказа/минимальная партия из 01/03 округляет предложение вверх; превышение max при кратности требует видимого предупреждения. Forecast/optimization лишь предлагают новую версию политики; не переписывают утверждённые нормы автоматически.

### 3.4 Решения покрытия — MM-02-04

CoverageDecision/Allocation связывает demand schedule/revision с источником, количеством в demand base UOM и actual material base UOM, типом STOCK/TRANSFER/PURCHASE/ANALOG, сроком, status PROPOSED/AUTHORIZED/EXECUTING/FULFILLED/CANCELLED и immutable snapshot коэффициента. Для комбинации 30 со склада + 20 перенос + 50 закупка на approved 100 допустимы три allocations; сумма действующего покрытия и net issued не выше approved quantity.

UI сравнивает пригодность, доступное количество, usable date, owner/purpose, просрочку, источник и ограничения. Рекомендованный порядок: свой свободный запас, межскладской перенос в срок, закупка остатка; аналог отдельным явно разрешаемым вариантом. Не заменять выбранный материал автоматически. Аналог допустим только по действующему направленному отношению 01, с разрешением применимости для назначения и snapshot: `actualAnalogQty = requestedBaseQty × factor`; округление определяется ЕИ и показывается до согласования. Нельзя переносить разрешение на обратное направление/цепочку аналогов без отдельного разрешения.

Commit перепроверяет demand version, approval, stock/source versions и лимиты. STOCK создаёт/переиспользует hard reservation. TRANSFER создаёт связанный документ 05 и origin allocation; прибытие позже due остаётся late coverage. PURCHASE создаёт PR только на выбранный непокрытый остаток, с lineage всех источников; 03 владеет группировкой закупочных документов и дальнейшим RFQ/PO. Создание PR — намерение, утверждение PO/графика — firm scheduled supply, приемка — физический запас: это переходы одной связи, а не три одновременных покрытия.

При receipt действующее allocation переходит от inbound к stock/резерву атомарно в пределах одного приложения. Остаток в карантине сохраняет статус blocked coverage. Условия перехода через consignment/ownership задаёт 06. Межфирменный/внешний запас только кандидат с необходимыми документами и датой доступности, не локальный свободный запас.

### 3.5 Резервы — MM-02-05

Существующий MaterialReservation сохраняется; `reservedQuantity` всегда текущий outstanding, не первоначальное количество. Сохраняется история released/consumed/cancelled/expired и добавляются события increase/reassign. Legacy `quantity` остаётся начальным значением; reconciliation использует initial + increases + transferredIn − releases − consumed − cancelled − expired − transferredOut = outstanding. Присвоение потребности/issue line — отдельная трассируемая связь; её нельзя молча переписать в старом событии.

Новые команды:

- `adjust`: `deltaBaseQuantity`, expectedVersion, reason. Положительная delta проверяет stock и demand headroom; отрицательная — только текущий остаток. Исполненное количество не редактируется. Для нового stock key создаётся связанный replacement reserve с атомарным освобождением старого; перенос между физическими складами всё равно требует документа 05.
- `extend`: newExpiresAt строго позже текущего времени и прежнего expiresAt, reason/version. Default лимит — до needByDate + 7 календарных дней; превышение требует MM_MANAGER/WAREHOUSE_HEAD и причины. Для бессрочного резерва использовать отдельное назначение срока; терминальный/уже истёкший резерв нельзя воскресить. Нужен новый резерв после проверки наличия.
- `reassign`: перенос всего/части outstanding на другой approved demand schedule/производственный/ремонтный заказ. Одновременные версии источника, назначения и резерва. Проверить company, материал/аналог, purpose, склад, ЕИ, срок; сохранить parent→child event/link. Остаток stock в сумме не меняется. Межфирменный перенос резерва этой командой запрещён; используется 05/06.
- create/reserve поддерживает `allowPartial=false` по умолчанию. false — всё или отказ; true — резервирует min(requested, eligible available, demand headroom), возвращает requested/reserved/uncovered. При нуле возвращает контролируемый insufficient-stock, не нулевой резерв. По нескольким партиям создаёт группу allocations с deterministic FEFO, без дробления серийной единицы.

IssueRequest должен потреблять существующие allocations demand reserve; не создавать второй резерв на то же обеспечение. Issued уменьшает outstanding и физический остаток ровно один раз через общий posting разделов 05/07. UI «потребить резерв» ведёт к документу выдачи/разрешённому stock posting с обязательным основанием; существующий API consume должен быть совместимым фасадом такого проведения либо отклонять недоказуемую физическую операцию. Фактический расход у получателя остаётся в 07.

Expiry идёт под системным scoped principal и теми же блокировками, что extend/issue. Кто первым фиксирует транзакцию, тот определяет исход; второй получает conflict. Expire/release не изменяют on-hand/value, только доступность. При блокировке/истечении годности резерв помечается AT_RISK и не позволяет выдачу; замена партии — отдельная audited команда.

### 3.6 Исполнение и производственный вход — MM-02-06

DemandFulfillmentAllocation связывает каждую проводку/строку документа с конкретным demand schedule и количеством (включая original/actual material). Проекции requested, approved, outstanding reserved, ordered cumulative/net cancelled, received gross/reversed/usable, issued gross/reversed/returned рассчитываются по связям. Не складывать этапы цепочки как независимое обеспечение. Для stock-only demand материал определяется самой строкой, не наличием PO. Для исторических пропорциональных связей выводить LEGACY_ESTIMATED; нельзя представлять их как точное подтверждение конкретному подразделению.

Return без сторно выдачи: по умолчанию net fulfilled уменьшается на принятое возвращённое количество и demand снова требует решения (сохранить потребность либо утвердить уменьшение). Исходный gross issued остаётся видимым. Возврат в карантин не даёт free stock. Получательское consumption в 07 отдельно от warehouse issue. Закрыть demand можно при net issued = approved либо утверждённом отказе от остатка; CLOSED с открытым резервом/незавершённым покрытием запрещён.

ProductionDemandIngressService применяет нормализованный вход через inbox раздела 10, а не из UI произвольным JSON. Контракт: sourceSystem, eventId, externalOrderId, externalLineId, revision, operation CREATE/REVISE/CANCEL, tenant/company mapping, department, production/repair/project reference, material mapping, quantity/UOM, needByDate, destination, priority, sourceOccurredAt. Уникальность по tenant/company/source/order/line/revision; одинаковый payload replay возвращает те же IDs, тот же ключ с другим payload — conflict. Старый revision не откатывает новый. Неизвестный материал/ЕИ/подразделение → REQUIRES_MAPPING, без пустой или автоматически согласованной потребности.

По умолчанию вход создаёт DRAFT operational demand со source reference и проходит MM approval. Автоматическое принятие доверенного MES допускается только отдельной утверждённой политикой и машинным scope; не включено по умолчанию. Правка/отмена использует те же impact/revision правила. Результат APPLIED содержит созданный demand ID/revision; RECEIVED/STAGED означает только получение сообщения. MES владеет составом/операциями производства, MM — материальным обеспечением. Подтверждения наружу — transactional outbox с correlation IDs, доставку проверяет 10; текущая фаза ничего провайдеру не отправляет.

## 5. Права, аудит, частичные операции, сторно и конкуренция

- Scope обязательный tenant + company, затем разрешённые подразделения/склады и purpose/ownership. Department worker создаёт/исправляет свои DRAFT и читает свои потребности; department head согласует в границах роли и SoD. MM_MANAGER консолидирует/планирует и выбирает закупочное покрытие. Warehouse keeper/operator резервирует/освобождает доступные ему stock keys; продление за policy limit, reassignment между заказами и override safety — warehouse head/MM_MANAGER с доступом к обоим назначениям. AUDITOR/VIEWER только чтение. Integration principal ограничен назначенным source/company, не ADMIN.
- Policy approval, substitute-use approval и demand approval не должны обходить общий approval engine. Caller не может подставить approvedBy, company, warehouse scope или вычисленные totals из DTO.
- Audit append-only: actor/service principal, timestamp, reason, command ID, before/after quantity/date/target/version, source document/line, approval task, UOM/analog/policy snapshots. Историю не менять generic PUT/DELETE. Source documents после проведения immutable; reversal имеет originalPostingId и отдельный approved reason.
- Коррекция stock facts поступает от posting владельца 05/07/08; 02 пересчитывает net fulfillment/coverage, а не переписывает проводку. Reversal выдачи может восстановить новый связанный резерв только если соответствующая потребность активна и stock eligible; иначе вернувшийся stock свободен/карантинен по факту приёмки. Исходный consumed reserve не «откатывается» без события.
- Для нескольких partial receipts/issues хранить отдельные allocations, с суммой не выше выбранного покрытия; частичная отмена PO возвращает только неполученный остаток в uncovered. Received и reserved могут представлять одно количество на разных этапах, а не суммироваться.
- Использовать существующие pessimistic stock/reservation locks и optimistic @Version. Общий порядок блокировок согласовать с 05/07: сначала canonical demand/coverage rows по ID, затем reservations по ID, затем stock keys по стабильному порядку (все участвующие команды должны следовать одному порядку). При deadlock bounded retry допустим только с тем же идемпотентным command key.
- Проверка demand headroom и суммы allocations выполняется в одной транзакции под блокировкой demand schedule. Два разных stock keys не позволяют двум потокам превысить approved quantity. На firm inbound allocation аналогично блокировать source schedule, чтобы суммарное pegging не превысило remaining incoming.
- Atomic commit: решение/резерв/связанный локальный документ/audit/outbox фиксируются вместе либо rollback целиком. Ошибка экспорта наружу не откатывает уже проведённый внутренний документ: pending/retry/reconcile по 10. Snapshot расчёта stale не основание исполнить старую доступность.

| 09 | Резерв/продление/переназначение не меняют стоимость; issue/reversal costing проводится владельцем stock posting. Закрытый финансовый период запрещает задним числом изменять исходные факты; новая плановая revision допустима с новой effective date. |
| 10 | Scoped command principal, approval/SoD, idempotency payload hash, inbox/outbox, audit, права и contract errors; mapping/replay/наблюдаемость производственных событий. Не отправлять сообщения поставщикам из 02. |
| 11 | Общие definitions/snapshot для shortage-at-due, late coverage, current reserves и исполнено. Drilldown/export до source lines; historical estimated attribution видна пользователю. |

Минимальный межраздельный факт: eventId, tenant/company, aggregateId/lineId/version, documentType, postingId, originalPostingId при сторно, demandScheduleId или sourceAllocationId, actual material/base quantity/UOM snapshot, effectiveAt/usableDate, source/destination stock key, status POSTED/REVERSED и correlationId. Это внутренний контракт, не обещание настроенного внешнего провайдера. Конкретное размещение общего DTO и миграций — один владелец 10/координатор.

Первая складская поставка должна включить: единый outstanding reserve и исправление двойного вычитания в views; резерв demand→issue без дублирования; partial issue/release/expiry и reversal links; scoped availability по stock key 05/06; ledger событий приёмки/переноса/инвентаризации, из которых будет строиться coverage. Extend/reassign можно поставить в этой волне после утверждения контрактов. Нельзя отключить действующие demand/PR workflows на время работ.

Следующая волна раздела 02: policy + расчёт по датам + mixed coverage, затем revision/consolidation + production ingress и полная прослеживаемость. Из неё ничего не вычеркнуто: MM-02-01/02/03/04/06 не становятся «завершёнными» от готового склада. Ingress на реальном MES остаётся unverified до provider confirmation; можно отдельно доказать локальное применение типизированного сообщения.

## 9. Решения по умолчанию для общего согласования

Координатор должен представить пользователю эти конкретные defaults вместе с другими разделами:

1. Approved quantity означает всю разрешённую потребность; закупается только выбранный остаток после stock/transfer/analog coverage. Старые sent documents не уменьшаются автоматически.
2. Резерв по умолчанию all-or-nothing; частичный — явный выбор. Ни emergency, ни новый заказ не забирают чужой резерв автоматически.
3. Нормы применяются по warehouse override/company default, уровни упорядочены как в §3.3; расход safety требует разрешения. Горизонт90 дней, даты компании; месяц без точного срока не разрешает выполнение до уточнения.
4. Аналог требует действующего master permission и разрешения применимости; коэффициент фиксируется, исходный материал не исчезает из истории.
5. Продление до needBy+7 дней — обычный scoped command, сверх — руководитель с причиной; бессрочность остаётся явной, expired не восстанавливается.
6. Вход MES создаёт DRAFT, автосогласование выключено. Ошибки mapping видимы, staged не считается applied; реальный provider отдельно проверяется.
7. Возврат уменьшает net fulfilled и открывает остаток до replacement либо новой approved revision. Закрытие потребности требует количественной сверки.
8. Нет разрушительного пересчёта истории: legacy receipt attribution и неоднозначные старые allocations помечаются и исправляются через reconciliation workflow.

Самопроверка проекта: все шесть IDs сопоставлены с текущим кодом, изменениями, зависимостями и A-сценариями; складской приоритет не удаляет дальнейшие процессы. Новая архитектура остаётся внутри текущего Java/React приложения. Разрешение на implementation, общий lock order, stock/UOM/owner контракты и migration numbering должны быть зафиксированы координатором в едином согласованном дизайне; до этого данный файл остаётся предложением.

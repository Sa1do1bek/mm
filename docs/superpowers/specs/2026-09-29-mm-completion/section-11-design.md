## 2. Alternatives and recommendation

1. **Recommended: dedicated report queries over operational evidence, with shared report definitions and reproducible results.** Keep the current dashboard and reuse availability/supply/supplier services, while splitting new register families out of the large ReportService. SQL aggregates and row queries share scope/filters/metric definitions. A bounded report run freezes rows and totals for identical paging and export. Domain sections continue to own facts. This offers immediate warehouse value and avoids a second transactional ledger.
2. Extend every existing report method and workspace independently. Lower initial setup cost, but filters, permissions, definitions and export totals would continue to diverge, and ReportService would grow further. Acceptable only for small compatibility adapters, not the final architecture.
3. Introduce an external BI warehouse/event projection first. Useful at much larger volumes but introduces lag, reconciliation, deployment and access-control duplication before the required source facts exist. Keep as a future scaling option behind the same report contract; not required for MM completion.

## 3. Proposed shared data and report API

Reports are read models, never a way to change stock, close a document or infer unsupported ownership. Reuse immutable movement allocations, transit entries, serial events, cost entries, inventory decisions and future custody/matching facts. Exact positions use tenant, ledger company, material, location hierarchy, batch and immutable StockContext; serial identity follows exactly one position/context. Labels can be localized but identity must not be text-based. Legal owner, typed holder, accountable person, operational state, earmarking and replenishment responsibility remain distinct; VMI metadata is not a stock-key dimension.

Create report-family definitions: `STOCK`, `MOVEMENTS`, `COVERAGE`, `EXECUTION`, `EXTERNAL_CUSTODY`, `RECIPIENT_RECONCILIATION`, `AGING`, `INVENTORY_RESULTS`, `VALUATION`, `INVOICE_MATCHING`, `SUPPLIER_PERFORMANCE`, `OPEN_WORK`. STOCK covers MM-11-01/02/03; other families cover the remaining IDs with shared drilldowns.

Proposed endpoints under `/api/reports/v2`:

- `GET /catalog`: available families, dimensions, authorized actions, definition versions, historical coverage start and dependency health.
- `POST /runs`: family, filters, grouping, sorting, locale and optional business as-of date; creates only a report artifact. Accept idempotency key for repeated generation requests. Returns run ID/status, effective authorized scope and timestamps.
- `GET /runs/{id}` and `/runs/{id}/rows?page=0&size=50`: status/metadata, complete scoped totals and stable pages. Allowed sort/group fields are enumerated per family; arbitrary SQL/expression input is disallowed.
- `GET /runs/{id}/export.xlsx` and `/export.pdf`: same frozen rows, filters, definition version, row counts and totals as the table. PDF is paginated tabular detail plus summary, not an unlabeled subset. Evidence links point to current authorized document views; a changed source is visibly marked newer than the run.

Filters: company IDs explicitly authorized within the tenant; site/warehouse/workshop/location/bin; material/group/base UOM; owner/holder/MОЛ/employee; batch/serial; project/order/contract; states; supplier; document type/status; period/as-of and monetary currency. Unsupported filter-family combinations fail validation rather than being ignored. Missing dimensions get an explicit `UNKNOWN` bucket and health issue, not an invented mapping. A row has an opaque stable `rowKey`, exact decimals serialized as strings, dimension IDs and labels, units/currencies, evidence references, and metric health.

`ReportRun`/`ReportRunRow` are proposed additive report-artifact tables, not business ledgers. Store tenant, initiating user, authorized company/scope fingerprint, family/version, normalized filters, locale/timezone, generated time, business cutoff, known-at cutoff, source health, status, row count, totals, content hash, expiry and ordered result rows. Generate with PostgreSQL repeatable-read in a single source-reading transaction; publish a run only when complete. Separate status writes mark failures. No partial rows masquerade as complete output. Recheck current permission against the stored scope on every read/download; revoke access if scope narrowed. A repeated generation key returns the same run. Default maximum is 50,000 output rows and 30 seconds source query time; exceed either with an actionable narrow-filter error and no truncated totals. Larger-volume background export is a subsequent capacity decision, not silent sampling. An asynchronous worker can generate the same bounded run without keeping an HTTP request open.

Default artifact retention is 7 days for rows/files; retain run metadata/hash under section 10 audit retention. Expired results return an explicit regeneration action. Section 10 owns retention/security policy approval. No report-run schema or indexes are added during this design phase; coordinator allocates additive migration versions after approval. Do not edit V1 baseline in implementation.

## 4. Metric and historical rules proposed for user review

1. **Time:** enterprise timezone defaults to Asia/Tashkent. Period UI dates map to half-open `[from start, day after to start)` boundaries. Current view means committed data known at generation; historical stock includes effective postings through business as-of and known by the run cutoff. Reservations, blocks and МОЛ assignments require effective history from their owners. Where that history predates migration coverage, display UNAVAILABLE with coverage start; do not reconstruct history from current mutable status. Re-running after an authorized backdated correction may yield a different known-at result; old runs remain unchanged.
2. **Quantities:** base UOM from section 1, document UOM/conversion snapshot available in detail. Never total different materials/UOMs into a single quantity KPI. Canonical operational states are USABLE, QUARANTINE, BLOCKED, REJECTED and approved additional states. Physical is the sum of all state quantities; free is eligible USABLE minus active reservations. Show ineligible USABLE explicitly when present. Reserved commitments on non-usable stock are separate analytical columns and are not added again to physical. Available foreign-owned quantity does not grant consumption permission. No report-side clamping hides negative anomalies. Company owned physical plus owned transit is an owned-position quantity; third-party stock is separate.
3. **Transit:** aggregate signed transit entries per shipment allocation. Dispatch removes warehouse physical and adds transit; receipt/loss resolution/return consumes transit once. Destination expected arrivals are a planning view of the same shipment, not another owned stock balance. Show restricted counterpart details only when authorized.
4. **Movements/reversals:** only POSTED evidence changes quantities/value (`B/enums/StockMovementStatus.java:14–18` currently enforces this concept). Original and reversal remain separate signed facts linked by identity. Partial reversals affect their actual allocations and dates. Current cancelled/draft document state does not erase previously posted evidence. Deduplicate by immutable event/line/allocation ID, not document number.
5. **Coverage/execution:** approved demand and eligible supply are allocated in section 2's dated order. Free stock already excludes existing reservations; reserved coverage for a target demand must not be subtracted twice. Expected quantities are outstanding accepted commitments, not full PO quantities after partial receipt. Stages in the execution funnel are not additive stock. Cancelled residuals remain visible separately from fulfilled quantities.
6. **Custody:** issue creates accountability; it does not prove consumption. Custody transfer preserves company-owned carrying value; actual consumption, loss and disposal have separately approved effects. Across a period, opening held + issued + incoming handover − consumed − returned − disposed/lost − outgoing handover ± approved corrections = closing held. For an original issue cohort, net issued = net consumed + net returned + net disposed/lost + still held across all successor holders; linked reversal terms remain explicit. These are projections of section 5 postings, not independently editable accountability quantities. Show both views, including overdue return and unacknowledged handovers. Contractor output is separately linked with section 6/7 yield/UOM rules, not subtracted as an arbitrary same-material quantity.
7. **Aging:** age starts at original receipt/acquisition lineage, not latest bin transfer. Buckets: 0–30, 31–90, 91–180, 181–365, >365 days; expiry: expired (< as-of), expires today, 1–30 days, 31–90, >90 and unknown. Section 8 decides operational blocking; the report never changes status. Non-moving threshold, activity basis and candidate decisions use the existing approved company/material policy version; no report-local 180-day default is introduced. New policy configuration must explicitly select its threshold/activity basis. Display aging buckets are analytical presentation only. Internal transfers do not reset original receipt age; whether they affect a configured non-moving metric is governed by that metric's approved policy. Keep case status distinct from a calculated slow/non-moving candidate.
8. **Turnover:** add period consumption quantity / time-weighted average owned physical quantity in the same material/base UOM; exclude internal transfers, show write-offs separately. Average uses daily closing balances across calendar days, including zero days; absent historical coverage makes this metric unavailable. Monetary turnover uses section 9's issued consumption cost / average inventory value and cannot mix currencies. Zero denominator returns null with reason. Preserve existing trailing-90-day issue-plus-write-off/current-free metric with its existing label/definition version.
9. **Inventory results:** latest valid count revision is the selected counted fact; superseded revisions are history. Difference, approved adjustment, posted adjustment and reversed adjustment are separate columns. Uncounted is null, not zero; unresolved observations are listed but not valued as stock. Separate shortage and surplus; show net only as an additional metric.
10. **Cost:** section 9 base-currency ledger and approved company/material valuation policy version are authoritative. Preserve existing methods; unmapped legacy ACTUAL_COST remains a visible reconciliation issue rather than receiving an assumed replacement method. Analytical valuation does not post carrying-value changes. Separate owned/third-party value, cost components, impairment and unallocated expenses; no cross-currency grand total or report-time FX conversion. Warehouse/material totals must not repeat on each batch. Price/quantity/tax tolerances and matching holds come from section 9, not a second reporting policy.
11. **Supplier:** show evaluation on-time/quality scores with evaluation count alongside transaction metrics. Default transaction timeliness: quantity received by original confirmed schedule due date / quantity due in the selected due-date cohort; approved revised-date performance shown separately. Exclude properly cancelled residual obligations but preserve cancellation history. Quality acceptance = accepted inspected quantity / finally inspected quantity; pending inspection is explicit. Zero denominator is unavailable. Do not combine dissimilar UOMs; a schedule-line OTIF measure is a separate count-based metric.
12. **Open work/errors:** use document-specific terminal/partial states from section 10, not `status != CLOSED`. Report age from the relevant pending transition and business deadline; absent deadline is unknown, not overdue. Count failed business messages distinctly from retry attempts. Read-only reports expose sanitized codes/messages, correlation IDs and retry state, not secrets/raw provider payloads. Provider acknowledgement and internal outbox success remain distinct.

These are defaults to approve centrally. They preserve every requested process; unresolved historical source coverage is a visible dependency, not a scope deletion.

## 5. UI, access, audit and error behavior

Extend `ReportsWorkspace` with report-family navigation and a shared filter drawer, keeping existing management analytics available. Each register shows active scope, generation/as-of timestamps, units/currency, source health, total count and unsampled totals, stable paged rows, grouping controls and source-document links. Warehouse users first see stock/transit, movement trace, aging and inventory results. Drilldowns preserve authorized filters and lineage. New snapshot after refresh is explicit; table and exports retain the selected run. A run error offers retry/narrow filters; PARTIAL identifies specific missing metrics; UNAVAILABLE never appears as a numeric zero. Loading, expired run, access revoked and empty valid result are distinct states. RU/UZ/EN copy belongs in the existing i18n system; keyboard and accessible table/filter controls follow existing Ant Design patterns.

Permissions must be applied **before aggregation** to queries, totals, source labels and exports. Existing roles are only an outer gate: warehouse staff get permitted warehouses, department users their permitted accountability/demand scope, procurement staff procurement/coverage/supplier data, finance cost/invoice fields, auditor read access inside granted organizational scope. Report read, cost read, personal custody read, multi-company read and export are separate capabilities mapped with section 10. Current company is default; authorized multi-company comparison preserves company partitions and currencies. Employee viewers see their own balances unless explicitly delegated. No recipient personal data or cost columns are sent and merely hidden client-side.

Audit generation/download with actor, report family/version, filters, effective scope, result count/hash and outcome, without copying sensitive values into generic logs. Access to an old run requires its entire stored scope still be authorized; do not partially redact rows while leaving old totals. Different users cannot fetch another user's run by UUID unless a specific report-sharing capability is introduced and approved. No provider message or posting command executes from report rendering/export. Correction/retry links enter the source workflow with its own action permission and concurrency/version checks.

Repeatable-read generation avoids torn balances/totals during concurrent posting. It must not take stock write locks. UI request cancellation or an idempotent retry must not create duplicate business effects. Read replica/projection deployment later requires explicit source watermark/lag, reconciliation and health; no such lag is assumed acceptable by default. Counts and monetary totals must reconcile to the same evidence/scope used by detail rows.

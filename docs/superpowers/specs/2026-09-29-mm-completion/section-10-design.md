# Раздел 10 — Общие функции документов

Дата исследования: 2026-09-29. Статус: предложение для единого согласования, **не разрешение на реализацию**. Все MM-10-01–12 остаются в объёме. Приоритет первого выпуска — складские операции и инвентаризация; общие контракты распространяются затем на остальные разделы.

Исследованы PROGRAM.md, REQUIREMENTS.md, MM-SCOPE-ASSESSMENT.md, WAREHOUSE-ACCEPTANCE.md, действующий исходный код двух репозиториев и явно запрошенные using-superpowers, brainstorming, writing-plans. `mm-front/AGENTS.md` запрещает автоматическое применение Superpowers, но здесь навыки запрошены явно. По ограничению координатора записан только этот файл: без реализации, миграций, Git-изменений, запуска сервисов, тестов или отправки сообщений провайдерам. Writing-plans используется для определения границ будущих задач; пошаговые планы появятся после общего approval gate brainstorming. Вопросы и предложенные политики ниже передаются координатору, отдельное согласование пользователю не направляется.

## 1. Вывод и варианты

Рекомендуется **адаптерный общий контракт поверх существующих доменных сервисов**. Сохраняем действующие receiving, transfer, inventory, approvals, attachments, costing и integration-health. Добавляем реестр типов документов и общий read-контракт, единые защитные правила команд и доказательства исполнения. Доменный сервис остаётся единственным владельцем переходов и проводок. Это устраняет неоднородность без переписывания всех документов и не создаёт второй складской регистр.

| Подход | Преимущества | Цена и риск |
|---|---|---|
| **A. Общие контракты + доменные адаптеры — рекомендуется** | Пошаговое подключение, переиспользование проверенных правил, единый UI и контроль покрытия | Требуется явная матрица возможностей каждого типа; адаптеры нельзя считать универсальным разрешением на запись |
| B. Исправлять каждую форму и сервис независимо | Меньше начальных изменений | Дублирование прав, подписей, retry и истории; новые типы вновь обходят проверки; дорого доказывать единообразие |
| C. Единая универсальная таблица документов и универсальный workflow engine для всех операций | Общая модель изначально | Массовая миграция работающих закупок/склада, потеря специальных ограничений, задержка первого складского выпуска; оснований для замены нет |

Нужен небольшой реестр доменных возможностей, а не новый low-code конструктор процессов. Проводки, стоимости, владение, единицы измерения и бизнес-согласования не дублируются разделом 10.

## 3. Предлагаемый контракт документов

### 3.1 Типы, header и реестр

`DocumentRef = {tenantId, companyId, documentType, documentId, lineId?}`; tenant/company сервер берёт из авторизованного контекста. Внутри компании UUID не даёт права доступа. В реестре каждого типа: header resolver, access policy, capabilities, lifecycle adapter, line-progress projector, relation provider, print/signature policy, retention policy, notification rules. Неизвестный тип закрыт. Применимые действия и блокирующие причины возвращаются сервером, но повторно проверяются при команде.

Header read model: number, operationDate, registeredAt, company, department, responsibleEmployeeId, creator, processStatus, approvalStatus, executionStatus, contentRevision, version, postedAt, effectiveReversalSummary. У existing полей остаётся свой authoritative owner. Supplemental metadata хранится лишь там, где доменная таблица поля не имеет; одинаковые значения не поддерживаются двумя независимыми writer. Каждый section adapter явно задаёт маппинг.

Нумерация по tenant/company/type/registration year, серверная последовательность, уникальный индекс; номера не переиспользуются, пропуски допустимы. Регистрация фиксирует номер; draft имеет UUID и временную метку. Legacy codes сохраняются как legacyNumber, не перенумеровываются молча. operationDate — business date в часовом поясе организации (по умолчанию Asia/Tashkent); registeredAt/postedAt — серверные моменты времени. Backdating допускается только в открытом периоде по полномочию. Подразделение и ответственный обязательны перед submit для операционных документов; для общекорпоративных документов explicit department scope=COMPANY и ответственный сотрудник. Для служебных импортов actor=service principal, бизнес-ответственный всё равно назначен.

### 3.2 Связи и исполнения

Доменная ссылка остаётся источником истины; общий relation index — транзакционно поддерживаемая проекция с source/target refs, relationType, sourceLine/targetLine, quantityBase, UOM snapshot ID, posting evidence ID. Типы: BASED_ON, FULFILLS, RETURNS, REVERSES, CORRECTS, SPLITS_FROM, CONSOLIDATES, FINANCIAL_HANDOFF. Index rebuild сверяется с источниками. Ручные пояснительные ссылки разрешены только как RELATED с audit, не учитываются в quantity caps. Граф оснований не допускает цикла; correction chains направлены на неизменяемые предыдущие версии. Запрос графа фильтрует каждый узел; скрытый чужой документ не раскрывает номер/сумму/контрагента.

`LineProgress` возвращает authoritative buckets по контракту раздела: requested, approved, reserved, ordered, dispatched, received, accepted, quarantined, returned, consumed, cancelledRemainder, reversed, open. У каждого bucket есть measure/UOM и evidence refs; не складываем разные единицы. Общий инвариант для одного выбранного исполнения: approved = netFulfilled + cancelledRemainder + open. Возврат не всегда уменьшает fulfilled: домен определяет, создаёт ли он требование замены. Transfer отдельно: dispatched = received + damagedHeld + unresolvedTransit + confirmedLoss + returnedToSource с учётом противоположных проводок; нельзя вычитать damaged twice. Custody отдельно: issued = consumed + returned + held, как у раздела 7.

Частичная бизнес-операция — отдельный зафиксированный execution event. Одна команда проведения атомарна для всех выбранных строк. Count draft batch может оставаться с per-row результатами; это редактирование наблюдений, не частичное проведение. Закрытие open remainder требует reason и согласованного полномочия; уже исполненное остаётся в истории. UI явно показывает закрытое количество и сохраняет исходный план.

### 3.3 Согласования и lifecycle

Существующие доменные статусы не заменяются одним enum. Общее представление разделяет draft/submitted/returned/approved/rejected; open/partial/complete; unposted/posted/partiallyReversed/reversed. Approval привязан к contentRevision и hash значимых header/lines/evidence. version меняется технически, contentRevision — только при значимом изменении. Любое изменение количества, получателя, стоимости, основания или обязательного evidence после submit возвращает на исправление и новое согласование. Печать/просмотр не изменяют contentRevision.

По умолчанию creator/responsible не может единолично approve собственный документ; самостоятельное согласование запрещено и для ADMIN. Делегирование с периодом и причиной сохраняет фактического и замещаемого approver. Отсутствие требуемого маршрута блокирует submit/post с диагностикой; auto-approval допустим только для явно настроенного низкорискового типа и фиксируется как решение правила. Inventory commission/finance approvals и procurement-specific маршруты сохраняются. Не добавлять второе независимое согласование поверх уже утверждённого доменного процесса.

## 4. Права, история, сторно и конкурентность

Проверки каждой команды: authenticate → resolve current company and document → action/scope authorization → idempotency replay authorization → lock → expectedVersion/contentRevision/state → business prerequisites → quantity/value mutation + result audit + outbox в одной DB transaction. Replay возвращает тот же committed business result только всё ещё уполномоченному пользователю; изменения разрешений и финансового masking учитываются при выдаче. Не сохранять в общем replay JSON секреты или неизменяемо раскрытые финансовые поля.

Разрешения: VIEW, CREATE, EDIT_DRAFT, SUBMIT, APPROVE, POST, ACCEPT, CANCEL_REMAINDER, REVERSE, PRINT, SIGN, ATTACH, REMOVE_DRAFT_ATTACHMENT, VIEW_AUDIT, VIEW_VALUE, RETRY_INTEGRATION, RECONCILE. Роли отображаются на эти действия, не создаётся второй источник пользователя/роли. Warehouse authorization проверяется для обеих сторон движения; при межфирменной передаче раздел 5 обеспечивает два отдельных документа и независимые полномочия. Receiver не получает доступ ко всей отправляющей организации. Query/export/download/link/notification имеют те же границы, что карточка.

Audit result содержит commandId, correlationId, actor/service principal, company, scope, action, reason, before/after revision/hash, quantity/value evidence, decision/approval instance и timestamp. SUCCESS сохраняется через текущую транзакцию; rollback оставляет только FAILED/ATTEMPTED в отдельном техническом журнале, без ложного POSTED. Прямые update/delete успешных проводок и решений запрещаются сервисом и ограничениями БД для runtime role. Добавления evidence после posting отдельными addendum events; старые файлы и их hashes не перезаписываются. Срок хранения не заявляется юридической нормой: предлагается отсутствие автоматического удаления до утверждения корпоративной retention policy.

Сторно создаёт новый документ/движение, ссылающийся на исходные allocation/cost layer/serial/evidence. Полное сторно не меняет строки оригинала; его summary status может отражать компенсацию. Частичное сторно ограничено remainingReversibleQuantity, считается под lock, причина обязательна. Если downstream issue/consumption/ownership transfer делает reversal невозможным, вернуть список препятствий и допустимый correction workflow; не брать другую партию, не допускать отрицательный остаток. Закрытый период: correction в текущем открытом периоде, либо approved reopen раздела 9. Signed original/PDF сохраняются, reversal подписывается отдельно по политике типа.

Idempotency key обязателен для создающих факт/внешнее событие команд, регистрации, submit/решения, post/reverse/accept/close-remainder/sign и execution imports. Scope = tenant/company/operation/resource/key, hash канонического payload включает expectedVersion. Claim ключа и business result атомарны; concurrent identical key ждёт завершения или получает понятный IN_PROGRESS, затем прежний результат. Changed payload = 409 IDEMPOTENCY_PAYLOAD_MISMATCH. Авторизация выполняется до cache lookup. Срок хранения ключей проводок равен сроку хранения факта; очистка не должна позволять повторное исполнение.

Порядок блокировок согласует раздел 5: document/line → canonical stock keys в одном сортированном порядке → allocations/serials → cost rows по согласованному порядку раздела 9. Existing material lock для отсутствующей balance row сохраняется до эквивалентной защиты полного нового ключа. DB uniqueness предотвращает два активных balance rows/serial assignments/fulfillment events. available=stock eligible for this operation − действующие чужие reservations с owner/status/quality/freeze ограничениями; own reservation потребляется ровно один раз. Preview availability не является гарантией. Deadlock retry допускается только для всей транзакции и того же command key с ограниченным числом попыток; внешняя отправка отделена outbox. Идемпотентность транспорта — at-least-once с дедупликацией, обещания exactly-once доставки нет.

## 5. Вложения, печать и электронная подпись

Использовать AttachmentService/storage, добавить registry coverage, content checksum, document revision binding, scan/validation status и preservation flag. Draft attachment можно удалить при полномочии; включённое в submitted/posted/signed evidence сохраняется, исправление — новая версия со ссылкой supersedes. Download проверяет документ и видимость финансовых сведений, а не только UUID файла. Неизвестный entityType отклоняется после миграции существующих допустимых типов в registry.

Печатные формы первого этапа: приход, расход/выдача, передача с частичной отправкой/приёмкой, возврат, инвентаризационная опись и сличительная ведомость, акт корректировки/сторно. Следующие этапы: открытие остатков, custody/смена МОЛ, спецзапасы/переработка/тара, quality/write-off/waste, procurement/service и invoice verification. Разделы владеют составом формы; раздел 10 — rendering/snapshot/version/access. Draft PDF имеет явную отметку «Черновик». Official PDF фиксирует templateVersion, contentRevision, hash, generatedAt и language; повторная загрузка той же версии возвращает те же байты. Финансовая и нефинансовая формы — отдельные разрешённые представления, blind count не раскрывает системное количество.

SignatureRecord: document ref/revision/hash, artifactHash, signer employee/principal/certificate subject, provider, verification status/result receipt, signedAt, verifiedAt, certificate validity evidence, correlation ID. Challenge строит сервер из snapshot; клиент присылает подпись этого challenge, а не произвольный payload. Положительная верификация требует явного verified=true и совпадения server hash/подписанта/полномочий/доверия по согласованному провайдерскому контракту. Пустой URL, disabled provider, timeout, неопределённый response — ошибка, без перехода SIGNED. Mock маркируется SIMULATED и не удовлетворяет обязательную production подпись. Повтор callback/verify не дублирует запись.

Предложенная policy для согласования: обычные внутренние складские операции используют authenticated approval; электронная подпись обязательна для типов/организаций, где это установлено требованиями предприятия, в частности внешних актов и передаваемых в ЭДО официальных документов. Матрицу обязательности утверждает пользователь централизованно; отсутствие выбранного реального провайдера означает «внешнее подтверждение не проверено», а не исключение MM-10-05. Юридическая применимость конкретной подписи не утверждается этим техническим проектом.

| ЭДО / ЭЦП | Доставка артефакта, проверка подписи и acknowledgement | Раздел 10 связывает remote receipt с конкретным revision/hash и не приравнивает HTTP 2xx к бизнес-принятию |

Новые inbox/envelope fields: eventId, sourceSystem, externalId, sourceVersion, schemaVersion, company mapping, eventType, occurredAt, correlationId, causationId, payloadHash, businessIdempotencyKey. Оригинальные payload/version append-only. UNIQUE(source scope/externalId/sourceVersion/eventType); тот же key/hash — replay, иной hash при той же версии — CONFLICT, не overwrite. Mapping/валидация проходит до apply; неизвестные material/UOM/owner/employee — карантин входящего сообщения с читаемой ошибкой, без частичного изменения склада.

Ingestion statuses: RECEIVED → VALIDATED → APPLIED, либо REJECTED/NEEDS_REVIEW; remote delivery statuses хранятся отдельно: QUEUED/DELIVERED/ACKNOWLEDGED/REJECTED. APPLIED означает наличие committed domain evidence ID, не просто ExternalInboundRecord. Out-of-order source versions удерживаются до predecessor или явной сверки. ACK подписывается/аутентифицируется по provider contract и проверяется по source/company/event/hash; секреты не попадают в audit/UI.

Существующий outbox расширяется lease/claim для нескольких workers, неизменяемыми attempts, stable business key и payload version. После сетевой неопределённости отправка повторяется с тем же business key. Operator replay создаёт transport attempt/new envelope с original reference, но сохраняет business key для того же факта; исправленное бизнес-содержимое требует нового versioned correction event. Существующие five-attempt/backoff значения допустимы как исходная policy, затем DEAD + действие оператора. Внешнее событие отправляется только после commit. Доменное проведение не откатывается из-за недоступности внешней системы; integration pending видно и может быть blocker закрытия периода по разделу 9.

Reconciliation run содержит system/company/date/window/watermark/key dimensions, ожидаемые и фактические business IDs, quantity/value/UOM/owner/status, differences, resolution document, operator/approval. Входящий WMS snapshot 97 при MM 100 создаёт discrepancy −3; только approved count/adjustment меняет MM stock. Дубликаты, missing acknowledgements, missing documents, quantity/value drift — отдельные категории. Reconcile не «чинит» ledger без документа. UI показывает очередь, attempts, очищенный payload, linked document, business acknowledgement, разницу и разрешённые retry/reconcile actions.

### 6.2 Уведомления

Rule adapters разделов предоставляют дедлайн/дефицит/действие и получателей; NotificationService отвечает за доставку и общий dedup key `(tenant, company, rule, document, occurrence, recipient)`. Предложение: один due-soon за 24 часа и один overdue при наступлении срока, escalation через один рабочий день; рабочий календарь/таймзона организации. Shortage — при появлении или изменении величины дефицита; approval/action — при новом assigned task; expiry/custody — по правилам разделов 7/8; DEAD/signature rejection — оператору и ответственному. Одинаковый scheduler run не создаёт повтор. Получатель проходит document access check; revoked permissions скрывают sensitive text и закрывают target. In-app обязателен; email/push только при настроенном разрешённом канале, без отправки реальным адресатам в acceptance.

## 7. API и пользовательский интерфейс

Предлагаемый additive read API: `GET /api/documents/{type}/{id}/context`, `/relations`, `/history`, `/execution`, `/artifacts`, `/signature-policy`. Context включает header, current revision, capabilities с reasonCode, scoped progress и ссылки на существующие command endpoints. Доменный POST `/receive`, `/dispatch`, `/post`, `/reverse` остаётся в соответствующем сервисе; общий controller не принимает произвольный status. Команды используют `Idempotency-Key`, expectedVersion, contentRevision при содержательных approvals/signing, reason при отклонении/исправлении/закрытии.

Artifact API: create print snapshot по type/template/revision/language; download immutable artifact; signature challenge/submit/status на конкретный artifact. Integration API: inbox detail/apply/reject, acknowledgements, reconciliation runs/differences/resolve; apply делегирует бизнес-команде. Для этих write endpoints обязательны те же command guard/access/audit правила. HTTP 400 — invalid envelope, 403/404 — authorization без раскрытия чужих объектов, 409 — stale/conflict/duplicate payload, 422 — бизнес-блокер; UI использует стабильные codes, а не парсинг текста.

Общий panel в существующих workspace: header с организацией/подразделением/ответственным/датами; вкладки «Исполнение», «Основания и результаты», «История», «Файлы и печать», «Подписи», «Обмен». Подключать по capabilities, сохраняя специализированные таблицы receipt/transfer/count. Прогресс показывает согласовано/исполнено/отменено/остаток и UOM по строкам. Action drawer отображает причину блокировки, требуемую независимую подпись/approval и preview эффекта. После timeout сохраняет payload/key для retry; после 409 показывает актуальное состояние, не отправляет изменённый payload со старым key. Dirty draft не теряется. Company switch меняет query cache scope и скрывает предыдущие документы. RU/UZ/EN, клавиатурная навигация и локализованные даты/единицы обязательны.

## 11. Предложенные решения для общего согласования

1. Принять подход A, доменные adapters и fail-closed registry; общий header/read API без переписывания всех сущностей.
2. Нумерация по company/type/year с допустимыми пропусками, отдельные operation/registration dates, обязательный бизнес-ответственный до submit.
3. Независимое согласование значимых документов; no-flow блокирует обязательный approval. Posted/evidence неизменяемы, correction/reversal отдельные факты; retention без автоматического удаления до корпоративной политики.
4. Атомарное posting выбранных строк, отдельный cancel remainder; частичное сторно только по доступному original allocation и approved domain policy.
5. Обязательные key/version и повторная авторизация replay; устранить legacy bypass одновременно с migration callers, без внезапной поломки работающего UI.
6. Подпись по корпоративной матрице типов/организаций, строго привязана к snapshot, mock явно SIMULATED. Конкретные обязательные формы, signer roles и доверенный провайдер утверждаются в общей review; отсутствие провайдера оставляет внешний gate открытым.
7. MM authoritative для своего inventory ledger; WMS snapshots используются для сверки. ERP/MES/ТОиР/LIMS/HR/ОС применяются через подтверждённые бизнес-команды и owner contracts; финансы сохраняют платёжные/банковские/амортизационные полномочия.
8. Уведомления in-app с дедупликацией, due-soon24ч/overdue/escalation1 рабочий день как начальная configurable policy; внешние каналы только настроенные. Warehouse-first закрывает общие safeguards раньше остальных workflows, но не уменьшает полный MM-10 объём.

Self-review: все 12 requirement IDs имеют source evidence, gap, предложенное поведение и acceptance; static findings отделены от runtime доказательств; складской этап и отложенные доменные/провайдерские зависимости перечислены; implementation approval отсутствует.

## Согласование с общими контрактами

Проверено по `CONTRACT-DECISIONS.md` (D01–D06); при расхождении терминов и политик этот общий документ имеет приоритет. Канонический неизменяемый `StockContext` содержит legal owner (`ownerPartyId`), типизированного держателя COMPANY / EXTERNAL_PARTY / EMPLOYEE / DEPARTMENT со scoped ID, optional `custodyAgreementId` и typed `earmarkId`. Подрядчик — EXTERNAL_PARTY, не отдельный тип CONTRACTOR; Employee/User не подменяет юридического собственника. Раздел 05 остаётся единственным авторитетом количественных проводок и проекций; accountability events раздела 07 — атомарные свидетельства/проекции этих фактов, без самостоятельно редактируемого количественного ledger. Подотчёт сохраняет принадлежащую компании стоимость. Применяется существующая утверждённая версия политики оценки компании/материала и действующие политики неликвидов; новый универсальный метод оценки/порог не вводится. Неоднозначный legacy ACTUAL_COST требует видимой сверки раздела 09. Финансовые настройки не заменяются инженерными defaults.

Возвраты по умолчанию поступают под quality hold; available/USABLE возникает только после зарегистрированного разрешения качества, в том числе как части разрешённого процесса приёмки. Физически принятые повреждённые/отклонённые материалы учитываются у фактического держателя с ограничениями. Неиспользованный возврат сам по себе не создаёт закупку взамен: раздел 02 фиксирует net fulfillment и решение об остатке потребности. Межфирменный процесс относится к компаниям текущего приложения; обязательной cross-tenant federation проект не требует. ## 4. Модель данных и инварианты

### 4.1 Общая адресация и происхождение

Каждый документ/строка/событие: tenantId, companyId, immutable id/number, operationDate, registeredAt, actor, version, основание и внешняя ссылка. Количества в base UOM плюс documentQuantity/documentUom/conversion snapshot раздела 01; серии требуют целого числа единиц и ровно такого количества MaterialUnit.

`MaterialAccountabilityPosition` — адрес обязательства, не второй stock balance: material/batch/serial, ссылка на канонический immutable StockContext (ownerPartyId, typed holder COMPANY/EXTERNAL_PARTY/EMPLOYEE/DEPARTMENT, custodyAgreementId, typed earmarkId), responsibleEmployeeId, departmentId, location reference общего раздела 05/06, destination context работ, dueBack/reportDue, condition/completeness snapshot. Holder и МОЛ независимы: кладовая цеха физически остаётся там же при смене ответственного. Для собственного сотрудника брать Employee, User — только учётная запись действия. Подрядчик адресуется как EXTERNAL_PARTY; identity/contract/ownership используют раздел 06, не дублирующий справочник.

`MaterialIssueAllocation` — одна фактическая аллокация частичной выдачи: issueRequestLineId, postingId/allocationId, stock key, serial ids, base qty, exact cost-layer references/value, destination position, demand line, limit commitment. Не перезаписывается следующей выдачей.

`MaterialAccountabilityEvent` — неизменяемое свидетельство: ISSUE, ACKNOWLEDGE, HANDOVER_OUT/IN, RETURN_ACCEPTED, CONSUMPTION, DISPOSAL, REVERSAL; source allocation, quantity/value, before/after holder/condition, document/line/posting ids, external evidence, actor/time. Количественный остаток — проекция авторитетных проводок раздела 05; события подотчёта атомарно связывают их с обязательством, подтверждением и историей. Подтверждение и смена только МОЛ имеют нулевой физический эффект. Событие не является отдельной редактируемой количественной проводкой и не списывает склад самостоятельно.

Новые документы: `MaterialHandover` + lines/confirmations; `MaterialConsumptionReport` + lines; `ProductionReceipt` + lines; `DismantledUnitReceipt` + lines. Лимиты: `MaterialIssueLimit` и ledger commitments/releases. Проверяемый `MaterialExecutionContext` с типом назначения и ссылками department, productionOrder, shift, workshop, repairOrder, equipment, project, constructionObject, contractor, contract; не универсальная непроверенная строка UUID. Справочный снимок внешнего заказа не даёт MM права менять график/операции работ.

ReturnLine расширяется accountabilityPositionId, sourceIssueAllocationId, accepted/rejected/pending portions, condition at handover/receipt, комплектность (expected/observed компоненты и missing reason), фактическая локация, attachment ids. Один возврат может включать несколько точных аллокаций; на каждую партию/серию и стоимость — собственная проводка.

### 4.2 Равенства и запреты

- Для исходной выдачи по всей цепочке держателей: **issuedNet = consumedNet + returnedNet + disposedNet + heldNet**. Для привычного отчёта «выдано–израсходовано–возвращено–осталось» disposed входит в суммарное закрытое выбытие с отдельной колонкой/расшифровкой, не маскируется производственным расходом. Без списаний применяется простое I = C + R + H.
- Для одного держателя: issuedTo + handoverIn − handoverOut = consumed + returned + disposed + held (все значения net of reversals). Передача не увеличивает issued всей исходной цепочки.
- PENDING_ACK, pending return, disputed и handover-locked — части held; видны отдельно, не вычитаются из равенства. Только физически принятое количество уменьшает held. Доступно к новому действию = held − committed pending portions; одна доля не может одновременно уйти в расход, возврат и акт передачи.
- Прикладной журнал подотчёта ссылается на физический holder stock раздела 05, поэтому consolidated owned stock считает эту долю ровно один раз. Складские available/reserved уменьшаются при выдаче; общий принадлежащий компании физический остаток уменьшается при фактическом расходе/списании, не при смене держателя.
- Точная стоимость передачи/возврата восстанавливается из исходных аллокаций. Для частичного количества деление выполняет раздел 09 с согласованной точностью и остатком округления на последней части.
- Нельзя принять невыданную серию обычным возвратом; снятый узел оформляется отдельным происхождением. Один serial не может одновременно находиться у сотрудника и на доступном складе.
- Снятие узла, ранее установленного на оборудование, не «сторнирует потребление» материала автоматически. Оно создаёт новое подтверждённое происхождение восстановленного узла и оценку, сохраняя связь с исходной серией/установкой. Если узел ещё числится в подотчёте, выполняется перемещение существующего остатка, а не новый приход.

## 5. Процессы и API

Имена новых endpoint — предлагаемый контракт. Существующие `/api/issue-requests` и `/api/returns` сохраняются. Ответы включают version, quantities, permittedActions/blockers, связанные документы, postings и ошибки на уровне строк. Все изменяющие команды требуют expectedVersion и Idempotency-Key; replay одинакового тела возвращает исходный результат, иное тело с тем же ключом даёт conflict.

### Выдача и подотчёт (MM-07-01, 02, 05)

1. Создать заявку с проверенным demand/context/department/receiverEmployee, назначением, сроком, UOM. UI показывает норму, остаток лимита, доступный запас и отклонение.
2. Submit → approve: независимый approver фиксирует approved quantity, версию нормы и limit commitment. Превышение — отдельный `/limit-exception` с решением, не скрытый флаг клиента.
3. Reserve по разделу 02. Issue передаёт только явно выбранные строки/количества; отсутствующая строка новой команды не должна автоматически означать «выдать всё». Для совместимости прежний клиент требует адаптации/версии контракта.
4. Каждая `/issue` атомарно проводит stock transfer to holder, обновляет резерв/лимит, создаёт IssueAllocation/held pending ack и audit/outbox.
5. `POST /api/material-accountability/allocations/{id}/acknowledge` или `/report-exception` фиксирует получение/расхождение; принятые части разблокируются. `GET /api/material-accountability/positions` и `/{id}/history` показывают личный/цеховой остаток с происхождением и сроками.
6. `POST /api/material-consumption-reports`, `/{id}/submit`, `/approve`, `/post`, `/reverse`: отчёт содержит исходные позиции/аллокации, фактическое количество, место/работу, дату, причину отклонения, подтверждающий документ. Утверждение отделено от автора; `/post` списывает holder quantity/value через общий posting, закрывает held. Принятое количество может быть меньше заявленного: остаток остаётся в held и не пропадает.
7. `POST /api/issue-requests/{id}/close` закрывает только исполнение с release остатка. `POST /api/material-accountability/positions/{id}/close` проверяет нулевое обязательство. `/extend-due-date` записывает причину и прежний срок. Просрочки отдаются разделу 10 для уведомлений.

### Акт смены МОЛ (MM-07-03)

`POST /api/material-handovers` → `/submit` → `/confirm-from` и `/confirm-to` → `/post`. Состояния DRAFT, AWAITING_CONFIRMATIONS, READY, POSTED, REJECTED, CANCELLED; отклонение освобождает hold, частичная передача оформляется явно принятыми строками/частями, непринятый остаток остаётся у прежнего МОЛ. Изменение состава после любой подписи создаёт новую revision и аннулирует подтверждения старой revision. Постинг одной транзакцией меняет ответственного/держателя по явно указанному типу акта. Печатная форма и вложения через раздел 10. `/reverse` требует обратного подтверждённого акта и доступности всей возвращаемой доли; после дальнейшего расхода — сначала зависимая корректировка.

### Возврат (MM-07-04)

Расширить `/api/returns`: create выбирает текущую позицию и исходную выдачу, submit фиксирует долю held, accept принимает фактическое количество и комплектность, остальное оставляет у держателя либо в явно зарегистрированном transit. Для поэтапной приёмки хранить received/accepted/rejected/pending; следующая команда обрабатывает только незавершённую часть, а не переписывает уже принятую. «Закрыть остаток возврата» требует решения и освобождает pending commitment, не списывает материал.

Раздел 08 владеет единым return origin/disposition и сервисом приёмки; раздел 07 добавляет конкретный origin ACCOUNTABILITY и атомарную сверку held. Нельзя одновременно разрабатывать два конкурирующих сервиса возвратов. Исправить committed query и quarantine-quantity вместе с тестами частичной приёмки по партиям.

### Производство, ремонт и строительство (MM-07-06, 07, 08)

`GET /api/material-execution-contexts` возвращает валидированные проекции MES/ТОиР/проектного контура и локальные разрешённые основания. Для productionOrder/shift/workshop, repairOrder/equipment, constructionObject/project/contractor один lifecycle: потребность → резерв → выдача → подтверждение → расход/возврат → сверка. Смена/цех задают контекст, но не заменяют держателя. Закрытый внешний заказ запрещает новую обычную выдачу, при этом сохраняет возврат и корректировку с разрешением.

Для подрядчика родительский holder/acceptance/contractor balance из раздела 06. Section 07 отвечает за назначение материалу на объект/монтаж и подтверждённый расход; Section 06 — передачу наружу, собственника, акт сверки и результат переработки. Одна проводка имеет обе ссылки. Неиспользованное возвращается тем же origin; расход материалов не равен акту приёмки стоимости работ раздела 03.

MES и ТОиР не получают команд управления своими работами из MM. MM возвращает обеспеченность и факты материальных движений через outbox. Входящая потребность идёт в раздел 02, не напрямую в увеличение лимита.

### Выпуск (MM-07-09)

`POST /api/production-receipts` и `/submit`, `/confirm`, `/post`, `/reverse`; импорт через типизированный inbound adapter раздела 10 создаёт тот же документ. Состояния DRAFT, AWAITING_CONFIRMATION, CONFIRMED, PARTIALLY_POSTED, POSTED, REVERSED. Строки классифицируются FINISHED_PRODUCT, SEMIFINISHED, RETURNABLE_WASTE и содержат материал/UOM/партию/серии/количество, источник заказа/смены/цеха, подтверждённый external line id, качество и оценку.

Ключ источника (tenant, company, sourceSystem, externalDocumentId, revision, lineId); семантическая ссылка на superseded revision предотвращает второй приход полной суммы при корректирующем событии. Подтверждённый выпуск 10 допускает приход 6 и затем 4; одинаковая доставка события не создаёт ещё 10. Превышение — отдельное исправленное подтверждение. Возвратные отходы производства приходуются здесь один раз, дальнейший жизненный цикл ведёт раздел 08. Нет автоматического равенства количества сырья и готовой продукции с разными единицами; технологический выход принадлежит MES.

### Снятые узлы (MM-07-10)

`POST /api/dismantled-unit-receipts` и `/submit`, `/confirm-source`, `/post`, `/reverse`; обязательны repairOrder, equipment/source installation, акт снятия, material identity/serial (или временный quarantine identifier с последующим сопоставлением), количество, комплектность, предварительное состояние. Уже известный serial сверяется с историей установки/остатком; конфликт удерживает документ без нового available stock. После поступления section 08 запускает quality disposition: пригодный → available, ремонтопригодный → blocked + ссылка обеспечения нового ремонта, непригодный → approved write-off. Материал не исчезает при выборе «списание» в выпадающем списке. При связи с ОС — акт исключения/замены компонента из контура ОС, без расчёта амортизации в MM.

Карточка по партии/серии показывает комплектность, текущий держатель/МОЛ, исходные выдачи и стоимость при наличии прав; действия возврата, расхода, передачи и продления срока.
- Отдельные формы акта смены МОЛ и отчёта расхода с таблицей конкретных позиций. Подписи показывают revision/hash, подписанта и время. Перед подтверждением видны количества и остающийся остаток.

Не показывать успешное проведение по одному состоянию кнопки. RU/UZ/EN, keyboard flow и компактный складской экран по существующим React/Ant Design patterns.

## 7. Атомарность, аудит, сторно и миграция

В одной транзакции: проверка tenant/company/department/warehouse/holder scope → блокировка document/limit/позиции/stock/serial → проверка versions/доступных количеств → проводка 05/09 → accountability/limit/reservation journal → audit/outbox → commit. Зафиксировать единый порядок блокировок с разделом 05 (document ids, context/limit ids, sorted stock keys/serial ids); противоположные handover не должны брать те же ресурсы в обратном порядке. Unique constraint на source posting allocation/event kind и идемпотентный ключ защищают повтор независимо от клиентского UI. Ошибка любого шага откатывает всё.

Параллельные return/consume/handover блокируют общую исходную долю, поэтому две команды не могут обе использовать один held. PostgreSQL-тест обязан проверять это на разных соединениях; optimistic version одного документа не защищает два разных документа расхода/возврата. Лимит также блокируется междокументно. Для истёкшего/отменённого pending документа commitment освобождается аудируемой командой, не физическим удалением.

Проводки неизменяемы. `/reverse` создаёт компенсирующие события со ссылкой на оригинал и точные аллокации, корректирует reservation/limit/accountability только в допустимом состоянии. Выдачу нельзя сторнировать, если её доля уже израсходована/возвращена/передана: сначала явная цепочка компенсаций; либо разрешённая частичная корректировка только свободной доли с отдельным документом. Прямой generic stock reversal для managed custody origins должен маршрутизироваться в orchestration 07 или блокироваться, иначе нарушит held. После закрытия периода — корректировка текущего открытого периода по политике 09, не изменение даты оригинала.

Audit содержит old/new snapshot для редактируемого черновика, immutable business events для проводок, reason, actor/delegate, timestamps, confirmations, attachments, исходную/новую revision, correlationId. Outbox не выполняет сетевой вызов внутри stock transaction. Повтор доставленного события не создаёт вторую проводку. Некорректная новая revision внешнего документа требует решения, а не silently applied snapshot.

Миграции только additive с номером, выделенным координатором после утверждения. Не менять V1. Ограничения: положительное количество события/строки, неотрицательные projections, уникальные source/external keys, tenant/company FKs и indexes для held/due/context. Сначала создать структуры и режим совместимости, затем выполнить сверяемый cutover.

Legacy issued − accepted returns не считается автоматически фактическим held: прошлые материалы могли быть израсходованы без отчёта. Создать reconciliation cases с флагом LEGACY_UNRECONCILED, предложенным количеством и реестром исходных движений; пользователь подтверждает opening custody либо документирует историческое закрытие. Исторический расход не списывает склад второй раз. Прежние ISSUE уже могли унести стоимость из складского ledger: восстановление на holder/переходной счёт — только решение 09 с reconciliation, не новое приобретение. При отсутствии точной партии/цены/серии данные не угадывать: заблокировать соответствующую коррекцию до решения. Новые документы сразу работают по новой модели; старые доступны для просмотра и контролируемой сверки.

### Specific correctness risks retained for investigation

`MaterialMapper.updateEntity` writes nullable batch/serial policy values before `MaterialService.beforeUpdate:246` runs validation queries; normalization runs later at `:261/299`. A JPA autoflush between those steps is a plausible explanation for the prior NOT NULL failures, not a reproduced root cause in this chat. `DB/V1__baseline_schema.sql:4630` requires batch policy NOT NULL. Proposed correction: construct and validate a complete candidate revision before mutating the managed entity; preserve omitted fields and normalize policy before any flush-capable query. The approved-change builder must preserve all unchanged fields, including tracking, material type, lead time and cost-selection evidence. Do not weaken the database constraint or assert a fix from mocks.

The baseline stock uniqueness already uses PostgreSQL `NULLS NOT DISTINCT` (`DB/V1__baseline_schema.sql:17096`). Preserve this protection when section 5 extends the key; an ordinary nullable unique constraint is a regression. `B/common/BusinessEntity.java:54` supplies optimistic entity versioning, but commands must also carry the version the user reviewed.

## 3. Approaches and recommendation

1. **Recommended: extend existing master governance and add small shared contracts plus a dedicated opening document.** Keep current cards, reference catalog, warehouses, attributes, duplicate queue and posting/cost engines. Add master revisions, material UOM conversions, typed sites/storage, certificate applicability and opening documents. This directly supports warehouse-first acceptance, preserves working UI and avoids separate sources of stock truth. Requires explicit shared-file ownership and contracts with sections 4–10.
2. **Add fields and route all openings through physical inventory.** Less initial code, but counts conflate opening value/cutover with operational discrepancies, cannot explain serial/ownership origin, and editable analog approval strings remain inadequate. Suitable only as a staging bridge, not full completion.
3. **Separate enterprise MDM service and import tool.** Strong independent governance boundary, but duplicates identity/security and adds synchronization/availability failure modes before warehouse operations work. Defer unless organizational system-of-record requirements demand it; full MM behavior stays in this application for this program.

## 4. Proposed design and default policies for coordinated review

All defaults below are proposals to approve centrally; none removes a requirement.

### 4.1 Material master and duplicate lifecycle — MM-01-01

- Keep company-scoped Material identity and existing group classification. A `MaterialRevision` records proposed complete content, source request, base material version, revision number, effective time, author, reviewer, decision and immutable approved snapshot. Existing active cards become an explicitly labeled migrated baseline, not falsely marked as historically approved.
- Use existing master request workflow DRAFT→SUBMITTED→IN_REVIEW→APPROVED→APPLIED, with rejection/revision/cancellation. Author cannot approve their own request. Apply is atomic with material/attributes/policy update; a changed target version yields 409 and requires a new diff/reapproval. No partial application of a card revision. Status metadata and actor IDs derive from authentication.
- Creation through the UI produces a draft request and duplicate candidates; active publication occurs only on apply. Restrict legacy direct card writes to an internal approved-apply path; update all UI callers/import paths. No browser-supplied approved flag bypass. Existing read DTOs remain compatible and add revision/allowedActions.
- Exact code/barcode/QR/RFID clashes block create using scoped database constraints as well as validation. Deterministic candidates use normalized article+manufacturer and group/name token similarity; name similarity is a review warning, never automatic merge. AI remains optional evidence. A rejected candidate records reason and input revision so changed data can be reconsidered.
- Merge means retire source and point to an active approved replacement. Do not rewrite historic movement/material IDs, combine quantities, or convert balances. A separate section 5 approved reclassification movement is necessary if stock identity must change. Replacement chains must not cycle.
- Default obsolete policy: prohibit new demand, procurement and unrelated receipt; permit approved disposition of existing stock, source-linked return, reversal, inventory counting and correction. Existing approved PO receipts against now-obsolete items require an explicit manager exception with reason. PROHIBITED blocks normal issue/use, but allows scoped quality handling and original reversal/return. Enforce at server commands, show reasons and replacement in selectors.

### 4.2 Characteristics, technical documents and approved analogs — MM-01-02

- Retain typed attribute templates per group, required/range/enumeration validation and RU/UZ/EN display. Approved revision snapshots attributes; new templates do not silently invalidate posted documents. New transactions use the effective approved revision.
- Add `MaterialTechnicalDocument` metadata: material ID, optional batch ID, kind SPECIFICATION/CERTIFICATE, revision, document number, issuer, validity interval, attachment ID/hash, supersedes ID, review status and authenticated approval evidence. Material-level specs and certificates differ from supplier accreditation certificates; links may reuse supplier evidence but do not equate it to batch conformity.
- Reuse AttachmentService/AttachmentEntityAccessPolicy for storage/access; no duplicate file store. Certificate edits create a revision. Historical downloads retain original evidence subject to the same company access. Missing/expired required certificate yields quarantine at receipt by default; section 8 controls release against validated evidence, never merely uploading a file. Specs show approval/validity and exact revision used on a receipt.
- Extend MaterialAnalog with DRAFT→IN_REVIEW→APPROVED→REVOKED/EXPIRED; authenticated reviewer distinct from proposer, immutable decision and effective interval. No generic status edit can approve. Eligibility requires both materials usable, current approval, validity, technical/use restrictions and no cycle.
- Define direction explicitly: `analogBaseQuantity = requestedOriginalBaseQuantity × numerator/denominator`. One-way by default; reverse use needs a separately approved reverse-use flag and reciprocal ratio on the same relationship, not a second edge that creates a graph cycle. Multi-material substitution chains remain forbidden at execution; selection uses a direct approved relationship. Existing conversionFactor is reviewed/mapped to this definition before enablement. This is substitution between materials, not UOM conversion. Order/reservation line retains original demand, selected analog, approval revision and calculated quantities; section 2 owns selection and section 3 supplier/order effects.

### 4.3 Shared UOM contract — MM-01-02, warehouse-first prerequisite

Add `MaterialUomConversion` with tenant/company/material, fromUomId, baseUomId, positive exact numerator and denominator, effective interval, approval revision, allowed use (purchase/receipt/issue/count), and quantity scale. Same-dimension standard conversions may seed defaults, but each material resolves an approved direct conversion to its base. Packaging is material-specific. No chained lookup, implicit density conversion, floating point, or silently inferred reciprocal.

Canonical calculation: `baseQuantity = documentQuantity × numerator / denominator`. Stock quantity storage currently has scale 4: retain it initially and reject values not exactly representable at the approved base quantity scale (max 4); serialized units require integer base quantities. Any future scale increase is a coordinated database/API change. Amounts and FX rules belong to section 9; document prices declare their price UOM, and amount preservation is tested independently of quantity conversion. No rounding may create/destroy physical stock.

Every relevant document line captures `{materialRevisionId, documentQuantity, documentUomId, baseQuantity, baseUomId, conversionRevisionId, numerator, denominator}`. Server computes and validates; clients preview only. Accepted drafts snapshot conversion at submission/approval; posting uses that snapshot. Superseding a conversion does not invalidate an already approved order: its conversion validity is evaluated at order approval business date. Explicit safety revocation blocks further posting and requires an approved amendment; it never recalculates quantities silently. A future conversion revision must not recalculate an approved order or posted movement. Reversal reuses original quantity and cost evidence. Section 9 additionally snapshots price quantity/UOM and currency/exchange evidence.

Proposed API: `GET/POST /api/materials/{id}/uom-conversions`; `POST /api/material-uom-conversions/{id}/{submit|approve|revoke}`; `POST /api/materials/{id}/convert-quantity` returns preview and revision. Existing `/api/uom` remains the unit catalog. A business-date conversion with ambiguous overlapping approvals returns a conflict; database exclusion/transactional checks prevent overlaps. Changing base UOM after any movement, reservation, serial or approved procurement use is blocked; use a replacement material and explicit conversion/reclassification document.

### 4.4 Organizational and physical hierarchy — MM-01-03

Add company-scoped `Site` (code/name/address/timezone/status). Warehouse gains siteId, warehouseKind CENTRAL/SHOP_STORE/EXTERNAL_CUSTODY and optional departmentId. Preserve Warehouse→StorageLocation→StorageBin. StorageLocation remains a zone; StorageBin gains physicalKind BIN/TANK plus capacityUomId and tank-specific permitted material/mixing constraints. A tank is an addressable physical stock position, not a quality/zone state. Shop stores remain real warehouses linked to department/site, with normal receiving/count/transfer behavior.

Retain existing IDs. Migration proposes a visible “Legacy site — mapping required” per company for unmapped warehouses, never silently maps one company into another. Site/warehouse/zone/bin parent consistency is checked in DB/service and every posting. Do not allow reparenting, disabling or deleting nodes with stock, reservations, open movements/counts or assigned serials. A tank cannot accept capacity overflow or forbidden mixing; section 5 owns atomic aggregate occupancy checks. Capacity quantities must use a declared compatible UOM; mass-to-volume requires an approved material/batch density measurement contract and cannot be guessed from liters/kg.

Add dated `StorageResponsibilityAssignment` (scope node, person, role, validFrom/To, acceptedAt, origin handover). Support multiple people/scopes with one accountable primary per scope/interval. Initial assignments are approved master setup; replacement of a person with stock requires section 7 handover and acknowledgements. Preserve existing Employee.warehouse as a compatibility view/adapter during migration; do not let editing that field silently move stock accountability. Stock posting snapshots responsible assignment; section 7 owns personal custody balances, not this catalog.

Proposed APIs: `/api/sites`; extend warehouse/bin DTOs; `/api/storage-responsibility-assignments` read/create and submit/approve/activate commands. Reuse warehouse tree UI, adding site, shop-store and tank badges, capacity units, assigned staff/history, and dependency-aware disable errors.

### 4.5 Tracking, shelf life and valuation policy — MM-01-04

Add approved `MaterialPolicyRevision`, linked to card revision: batch NONE/OPTIONAL/REQUIRED; serial NONE/REQUIRED; expiry required flag, shelfLifeDays, minimum remaining life on receipt, certificate requirement, retest interval and valuationMethod/effective date. Keep existing enums and derive legacy trackingMode; never make it a second authority. New TMB tracking defaults remain NONE/NONE unless approved group policy requires tracking. Valuation uses the approved company/material policy version under CONTRACT-DECISIONS.md D02; there is no universal new ACTUAL_COST default. Existing ACTUAL_COST settings remain visible and require explicit mapping/reconciliation if their semantics are ambiguous. No silent default expiry extension or valuation conversion.

A receipt of a required-batch material must provide batch identity; required serial material must provide exactly one unique serial per base unit. Batch+serial is supported concurrently. Manufacturing date cannot exceed receipt business date, expiry cannot precede manufacture, and conflicting expiry fields are rejected; consolidate StockBatch.expirationDate/expiresOn through one canonical API value and compatibility read mapping. Certificates/expiry are evaluated at receipt and at issue; default overdue material goes to blocked/quarantine handling under section 8. Retest approval creates dated evidence, not an overwritten expiry field.

Changing NONE to required tracking while stocks or open documents exist requires an approved migration/re-identification process jointly owned with sections 5/8, and is blocked until all relevant units are identified. Disabling tracking with any trace history is blocked; create a successor material if necessary. Valuation change requires section 9 permission, open-period policy and prospective effective date, with required revaluation evidence; a generic card update cannot rewrite costing. Preserve all historic policy snapshots for trace reports.

MaterialUnit must support exactly one immutable origin: existing receipt-unit evidence OR approved opening-line evidence. Propose originType/originDocumentId/originLineId plus nullable legacy receipt references and a database check enforcing the valid combination. Backfill existing units to RECEIPT with no loss of lineage; do not fabricate supplier receipts for openings. Sections 4/5 own the shared serial lifecycle implementation; section 01 supplies opening provenance. MaterialUnit.warehouseId is also currently mandatory: sections 5/6/7 must decide how external/personal holding is represented in their shared location/holder model before A16, retaining last-warehouse provenance without falsely counting those units as warehouse-available.

### 4.6 Opening balance workflow — MM-01-05

Create `OpeningBalanceDocument`, `OpeningBalanceLine`, `OpeningBalanceControlTotal`, and append-only posting/reversal evidence. Reuse DataMigrationRun/Row for raw file and validation provenance; support manual entry with identical validation. Header includes company, cutover business date, source system/extract ID/hash, stock-scope partition, reference mapping version, accountable owner of reconciliation and approvals. Lines include material revision, complete location, batch/manufacture/expiry, serials, stock owner, holder, stock category/status, earmark, responsible assignment, document/base UOM snapshots, quantity, carrying value, currency, source row/key and attachments.

Lifecycle: DRAFT→VALIDATED→IN_REVIEW→APPROVED→POSTED; reject to editable draft via a new revision, cancel before posting, reverse posted evidence through a linked command. Validator resolves tenant/current-company IDs, never code alone or best-effort cross-company lookup. Unknown material/location/owner/responsible/required serial/currency is a blocking error. Warning waivers require reason and permitted decision maker; they cannot waive physical identity, ownership, arithmetic or authorization invariants.

At validation, compare source control totals with staged and approved totals by material/base UOM, owner, warehouse/status and currency. Never sum incompatible UOMs or currencies. At posting, reconcile ledger quantities, serial counts and value deltas against the approved preview. For own stock require explicit carrying value; zero value requires a finance-approved reason. Foreign-owned stock records physical quantity and owner-declared memorandum value, with zero company-owned asset value unless section 6/9 says ownership transferred. Default cutover is company-local business date; mixed-currency openings require approved section 9 exchange snapshots.

Opening is allowed only in an explicitly unopened partition at cutover, with no existing transactions/balances that would be duplicated. Use a cutover registry and posting lock for both opening and ordinary stock commands. Historical cutover with later movements is blocked, requiring a deliberate migration/reconciliation path. After a partition is opened, corrections are linked adjustments; no new “opening” may add the same stock twice.

Posting is atomic per approved document/partition, including stock ledger, cost layers, serialized identities, responsibility provenance and outbox/audit. Section 5 provides the posting service contract and section 9 costing; no direct repository edits to balances. Large files may be deliberately split into disjoint child partitions before approval. Never silently post only valid rows. Parent reconciliation remains incomplete until every partition is posted or explicitly excluded by an approved cutover scope revision; “excluded” data remains visible, not lost.

Idempotency is scoped by tenant/company/document/command with payload hash; the same key returns the same result, a changed payload conflicts. Also prevent duplicate source-system/extract/source-row imports across documents, plus overlapping cutover partitions. Serial uniqueness is enforced by database constraints including concurrent imports.

Reversal defaults to whole-document exact reversal when all original stock/value/serial allocations remain available and period is open. If downstream consumption/transfer exists, reject with references and require dependent reversal or an approved correction using remaining lineage. Partial correction uses a separate approved document with explicit line/quantity/value bounds; it cannot rewrite the initial source control totals. Reversal preserves origin and serial history, with reversal events marking current availability appropriately.

Proposed APIs: `/api/opening-balances` list/create/get/update-draft; `POST /api/opening-balances/{id}/{validate|submit|approve|post|cancel|reverse}`; `GET /api/opening-balances/{id}/reconciliation`; `POST /api/migration/runs/{id}/opening-draft` idempotently creates a draft from selected validated partitions. Commands require expectedVersion; financial approval is a distinct assigned approval task. API returns structured row errors, blockers, quantities/values and allowedActions.

UI: extend DataMigrationPage with “Create opening document”; a dedicated OpeningBalanceWorkspace shows source vs staged vs approved vs posted totals, mapping errors, ownership/responsibility, duplicate source rows, serial counts and line evidence. The review/post dialog presents exact scope/date/count/quantity/value effects. Posted rows link to ledger/cost/serial trace; conflict reload preserves unsent edits. Inventory count remains a separate section 8 workflow.

## 5. Permissions, audit, partial operations and concurrency

Existing baseline: `B/security/SecurityConfig.java:32–36,102,146` groups master/warehouse/migration endpoints; `B/controller/MaterialMasterRequestController.java:25,102–157` adds ADMIN/MM_MANAGER command roles. These are retained as coarse access, supplemented with scoped action permissions and separation of duties; existing authentication is not proof of new-command authorization.

| Action | Proposed default authorization and boundary |
|---|---|
| View master data | Existing read roles, current tenant/company; warehouse details only within assigned warehouse scope. Auditor is read-only. |
| Propose card/analog/conversion | MM_MANAGER or assigned master-data steward capability; no self approval. Catalog admin assignment is separate from ADMIN technical role. |
| Approve/apply master revision | Assigned independent MM approver; quality approval additionally for certificate/technical restriction; finance controller for valuation/base-price implications. |
| Maintain sites/storage | Scoped MM_MANAGER/WAREHOUSE_MANAGER; responsible-person transition with balances requires section 7 acknowledged handover. |
| Stage/opening draft and reconcile quantity | Scoped warehouse keeper/manager; upload access does not imply post access. |
| Approve opening value | Assigned FINANCE_CONTROLLER/ACCOUNTANT capability, independent from preparer; approved quantity and value decisions both required. |
| Post/reverse opening | Assigned scoped posting capability after approvals and open-period checks; reversal requires reason and equivalent approval. ADMIN alone cannot bypass company, period or self-approval controls. |

For every mutation record actor IDs, business/system times, before/after revision or immutable hash, source request, decision/reason, expected version, command/correlation ID, and resulting ledger IDs. Financial evidence is append-only. Do not place attachment contents or sensitive employee data in generic audit text. Scope all child IDs, search results, exports, attachments and command references, including cross-company administrator sessions.

Quantity conversion never partially succeeds. Card revision application is atomic. Opening partition posts atomically; retry is safe. Conversion interval changes and duplicate candidate merge lock/check both affected cards in stable ID order. Opening locks cutover partition and stock/serial keys in deterministic order; ledger/cost/serial/outbox commit together. A stale 409 returns current version and blocker details; frontend does not auto-retry a changed business decision. Master-reference version changes between approval and posting require either the original approved snapshot or explicit revalidation; never an unnoticed recalculation.
